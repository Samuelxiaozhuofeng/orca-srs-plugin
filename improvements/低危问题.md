## 1. 零卡片仓库每轮收集都触发 get-all-blocks 全库扫描兜底

- **位置**：`src/srs/cardCollector.ts:147`
- **审计维度**：性能与批量读取
- **状态**：待处理

### 问题描述

collectSrsBlocks 仅以 `tagged.length === 0` 判断是否走兜底,不区分『查询失败』与『查询成功但确实没有带 #card 的块』。对尚未创建任何卡片的仓库(或卡片全被删光后),每次收集——包括 Flash Home 挂载、每个评分事件、120s 定时器(且叠加发现 3 的双份收集)——都会执行一次 `get-all-blocks` 无界全库读取并在内存中过滤,与 AGENTS.md『Bound bulk block reads…no unbounded Promise.all over the repository』的意图相悖。incrementalReadingCollector.collectTaggedBlocks 有同样问题:它虽然记录了 querySucceeded,但兜底条件仍只看 tagged.length===0。

### 代码证据

cardCollector.ts:147-151:
```
if (tagged.length === 0) {
  console.log(`[${pluginName}] collectSrsBlocks: 直接查询无结果，使用备用方案`)
  try {
    const allBlocks = await orca.invokeBackend("get-all-blocks") as Block[] || []
```
incrementalReadingCollector.ts:184-187 同构:`if (tagged.length === 0) { ... await orca.invokeBackend("get-all-blocks") ... }`(querySucceeded 只用于最终抛错判断,不阻止兜底扫描)。

### 修复建议

在两处都记录标签查询是否成功(cardCollector 目前完全没记录),仅当 get-blocks-with-tags 两个变体全部抛错时才走 get-all-blocks 兜底;查询成功且为空时直接返回空结果(state 里的 _repr 块合并逻辑保留即可)。

## 2. retrySequentialActivation 对同一章节块最多串行 get-block 4-5 次

- **位置**：`src/srs/book-ir/bookIRProgression.ts:432`
- **审计维度**：性能与批量读取
- **状态**：待处理

### 问题描述

顺序书修复路径对 plan.selectedChapterIds 做了多轮逐章严格后端读取:先 listLiveSequentialChapters(每章 1 次 get-block)、再 listPartialSequentialChapters(每章又 1 次)、清理循环里对每个非目标章节连续调用 isChapterFullyActive + chapterHasAnyBookIR(同一块背靠背再读 2 次)、最后再 listLiveSequentialChapters 复扫一遍。一本 100+ 章的书单次修复约 400-500 次串行 get-block 往返,且同一块被重复读取。属恢复路径、触发频率低,但章节多的书会明显卡顿。

### 代码证据

bookIRProgression.ts:318-319 `listLiveSequentialChapters(...)` + `listPartialSequentialChapters(...)`;432-435:
```
for (const chapterId of plan.selectedChapterIds) {
  if (chapterId === targetId) continue
  const live = await isChapterFullyActive(chapterId, bookBlockId)
  const partial = await chapterHasAnyBookIR(chapterId, bookBlockId)
```

### 修复建议

每一轮判定前用一次批量 `get-blocks`(复用 prefetchBlocksByIds 模式)拉取全部 selectedChapterIds 的最新块,把 isChapterFullyActive / chapterHasAnyBookIR 改造成接受 Block 的同步谓词在内存中判定;『strict 后端读』语义只需保证每轮判定用的是同一次新鲜批量读取即可,清理后的复扫再批量读一次。

### 独立验证结论

## 3. cleanupSrsProperties 删除全部 srs.* 属性后不失效块缓存,失败路径可能复活已删除的复习进度

- **位置**：`src/srs/tagCleanup.ts:40`
- **审计维度**：缓存一致性
- **状态**：待处理

### 问题描述

cleanupSrsProperties 通过 core.editor.deleteProperties 删除块上全部 srs.* 属性,但整个文件没有任何 invalidateBlockCache 调用,违反 AGENTS.md 硬规则『每次块属性写入后必须失效对应缓存』。当前唯一调用点 cardCreator.ts:257 紧接着调用 writeInitialSrsState,靠后者内部的 blockCache.delete(storage.ts:388)兜底才没有出事。但如果 writeInitialSrsState 抛错(删除成功、初始化失败),或未来任何调用方单独复用这个辅助函数,长期存活的 blockCache(生产路径从不 clearBlockCache,见 storage.ts:95 注释『生产路径依赖 invalidateBlockCache 做精确失效』)会继续持有含已删 srs.* 属性的旧块:ensureCardSrsState(storage.ts:639 经 getBlockCached 读取)会误判 hasAnySrsProps=true,跳过重新初始化并把已删除的旧复习进度当作现行状态返回,与后端真实数据(无任何 srs 属性)分叉。

### 代码证据

tagCleanup.ts:40-45:
  await orca.commands.invokeEditorCommand(
    "core.editor.deleteProperties",
    null,
    [blockId],
    propertyNames
  )
(函数到此结束,无 invalidateBlockCache)。对比同仓库同语义的 storage.ts:796-803 deleteCardSrsData 在 deleteProperties 后有 blockCache.delete(blockId)。调用点 cardCreator.ts:256-258: if (!hasCardTag) { await cleanupSrsProperties(blockId, pluginName); await writeInitialSrsState(blockId) }

### 修复建议

在 cleanupSrsProperties 的 deleteProperties 之后立即调用 invalidateBlockCache(blockId)(从 ./storage 导入),使辅助函数自身满足硬规则,而不是依赖调用方后续写入碰巧失效缓存。

### 独立验证结论

证据全部属实:tagCleanup.ts:40-46 调用 core.editor.deleteProperties 后函数直接结束,整个文件无任何 storage 导入或 invalidateBlockCache/blockCache.delete 调用;对比同语义的 deleteCardSrsData(storage.ts:795-803)在删除后确有 blockCache.delete(blockId)。唯一调用点 cardCreator.ts:257 紧跟 writeInitialSrsState(→saveCardSrsState→saveSrsStateInternal,storage.ts:388 blockCache.delete)兜底;clearBlockCache 在生产路径确实从不调用(仅 cardCollector.ts:306-309 的 resetCollectCachesForTests,注释明确"仅用于基准隔离"),缓存长期存活。故硬规则『每次块属性写入后必须失效缓存』的违反是真实存在的。但影响被显著夸大:失败路径要求"deleteProperties 成功且紧接着的 setProperties 抛错"这一罕见双重条件;且即便发生,makeCard 流程在 line 212 已先给块加上 #card 标签,下一轮 collectReviewCards 必经 cardCollector.ts:229 preheatBlockCache(blocks)——collectSrsBlocks(cardCollector.ts:130)从后端 get-blocks-with-tags 取回新鲜块,preheatBlockCache(storage.ts:87 blockCache.set)会覆盖同 id 的陈旧条目,ensureCardSrsState 随即看到无 srs 属性并重新写初始状态,自动修复(disableOptimizations 仅测试用)。评分(grading)总是在收集之后发生,卡片状态已被 preheat 刷新,不存在把陈旧进度写回后端的持久化污染路径。残留风险仅为:失败后到下一轮收集之间,重试 makeCard 走 cardCreator.ts:261 ensureCardSrsState 会读到陈旧缓存、跳过重初始化并返回已删状态——但该路径不写任何数据,后端保持干净,属短暂展示级偏差且自愈。综上问题真实(违反硬规则+存在窄失败窗口),但无持久数据损坏路径,severity 应降为 low 而非 medium。

## 4. 选择卡统计的写入与清除(srs.choice.statistics)不失效 blockCache
