## 1. IR 资料库全量收集对每个块串行发起 backend get-block,且块数据已在手仍重复读取

- **位置**：`src/srs/incrementalReadingCollector.ts:422`
- **审计维度**：性能与批量读取
- **状态**：已修复（2026-07-26）

### 问题描述

collectAllIRCardsFromBlocks 用 `for...await` 完全串行遍历全部 IR 卡块,每块经 ensureIRState/loadIRState → irBlockCache.getBlockCached 首次 miss 时发起一次 backend get-block。而传入的 blocks 本身就是刚从 get-blocks-with-tags/索引拿到的完整块(含 properties),却没有像 SRS 侧 cardCollector 那样 preheatBlockCache,导致同一块被后端重复读取。该函数被资料库首屏 useIRWorkspaceLibrary.loadLibrary → collectAllIRCards 调用,IR 库有 N 张卡就是 N 次串行后端往返;同文件的到期收集 collectIRCardsFromBlocksDetailed 虽有 mapPool 并发 8,但同样存在整批重复读取。

### 代码证据

incrementalReadingCollector.ts:422-430:
```
for (const block of blocks) {
  ...
  if (!readOnly) {
    await ensureIRState(block.id)
  }
  const state = await loadIRState(block.id)
```
irStatePersistence.ts:38 `const block = await getBlockCached(blockId)`;irBlockCache.ts:19 `const block = (await orca.invokeBackend("get-block", blockId))`。全仓 grep 确认 incremental-reading 目录无任何 preheat 入口;useIRWorkspaceLibrary.ts:68 `const cards = await collectAllIRCards(name)` 为资料库首屏路径。

### 修复建议

为 irBlockCache 增加 preheat 接口(参照 storage.ts:83 preheatBlockCache),collectAllIRCardsFromBlocks / collectIRCardsFromBlocksDetailed 入口先用已在手的 blocks 预热缓存,使 loadIRState 走缓存命中;collectAllIRCardsFromBlocks 的串行 for 循环改用已有的 mapPool(COLLECT_CONCURRENCY)。

### 独立验证结论

属实。incrementalReadingCollector.ts:422-430 确为串行 for...await,每块经 ensureIRState/loadIRState → irStatePersistence.ts:38/203 getBlockCached → irBlockCache.ts:19 cache miss 时 invokeBackend("get-block")。传入 blocks 来自 collectCandidateBlocks(collector.ts:216-279),已含完整 properties(函数自身 418-420 直接用其做 readIRSourceMeta),索引路径(232-240)还已逐块 get-block 过一次,冷缓存下同块被后端重复读取。全仓 grep 确认 preheat 仅存在于 SRS 侧(storage.ts:83、cardCollector.ts:229),irBlockCache 无预热接口。首屏路径确认:useIRWorkspaceLibrary.ts:63-68 loadLibrary await collectAllIRCards(name) 且未传 readOnly,每块还多跑一遍 ensureIRState。同文件 336 行注释自证项目视串行 N+1 为首屏问题并在 collectIRCardsFromBlocksDetailed(mapPool 并发 8)修复过,唯独此函数遗漏。severity 降为 medium 的理由:irBlockCache 是模块级持久 Map(irBlockCache.ts:7),仅按块写入失效,N 次串行往返主要在插件启动后首次打开资料库时发生,后续多命中缓存;纯性能问题,无正确性/数据风险,get-block 为本地 IPC,需较大卡库才明显。

## 2. IR 索引路径逐 id 串行 get-block,未使用批量 get-blocks

- **位置**：`src/srs/incrementalReadingCollector.ts:233`
- **审计维度**：性能与批量读取
- **状态**：已修复（2026-07-26）

### 问题描述

collectCandidateBlocks 走 IR 索引命中路径时,对索引里全部 topicIds+extractIds 逐个 `await orca.invokeBackend("get-block", id)`,完全串行、无批次、无并发上限。该路径在每次 IR 收集(到期队列、今日学习摘要、资料库)都会执行,库有几百上千张卡时就是几百上千次串行后端往返;而仓库已有现成的批量方案 storage.prefetchBlocksByIds(get-blocks,批 50、并发 4)。且这批块随后又被发现 1 中的 loadIRState 二次逐块读取,单轮收集每块合计 2 次后端读。

### 代码证据

incrementalReadingCollector.ts:229-239:
```
const ids = [...index.topicIds, ...index.extractIds]
const blocks: Block[] = []
let missing = 0
for (const id of ids) {
  try {
    const block = await orca.invokeBackend("get-block", id) as Block | undefined
    if (block) blocks.push(block)
    else missing += 1
  } catch {
    missing += 1
  }
}
```

### 修复建议

改用 `get-blocks` 分批读取(直接复用 storage.ts 的 prefetchBlocksByIds/runBoundedConcurrency 模式,批 50、并发 4),并把结果预热到 irBlockCache;missing 统计可由『请求 id − 返回 id』差集得出,行为(30% 失效回退全量)保持不变。

### 独立验证结论

属实。incrementalReadingCollector.ts:229-240 确认索引命中路径对全部 topicIds+extractIds 逐 id 串行 orca.invokeBackend("get-block")，无批次无并发，且绕过 getBlockCached 不预热缓存；irIndex.ts:10 显示索引新鲜期 10 分钟，期间每次收集都走此路径；调用方为首屏路径（useIRWorkspaceSession.ts:97 到期队列、todayLearningSummary.ts:541 今日摘要、useIRWorkspaceLibrary.ts:68 资料库）。后续 loadIRState（irStatePersistence.ts:38 → irBlockCache.ts:19）冷缓存下对同一批块二次 get-block，双重读取属实。storage.ts:125/175/225 确认已有 prefetchBlocksByIds（get-blocks 分批+有界并发）可复用。文件内 337 行注释自称已避免顺序 N+1，但仅覆盖第二阶段，候选收集阶段仍纯串行。降级理由：纯性能问题（本地 IPC 单次开销小），无正确性/数据风险，仅大库+索引新鲜窗口内有秒级影响，故 high 夸大，定为 medium。

## 3. Flash Home 每次加载把全库 collectReviewCards 连跑两遍(含 120s 定时器)

- **状态**：已修复（2026-07-26）

SrsFlashcardHome.applyLoaded 先 `loadFlashHomeData`(内部 collectReviewCards 全库标签扫描+预取),紧接着 `loadTodayLearning(true)` 强制绕过 45s 缓存,而 loadTodayLearningSummary 内部又独立调用一次 `deps.collectReviewCards(pluginName)`,不复用刚拿到的 cards。结果是:组件挂载、每个 SRS 事件刷新、以及 120s 兜底定时器(force:true,即使面板在后台)每次都对整个仓库做两遍完整 SRS 收集,外加一遍完整 IR 收集链(叠加发现 1/2 的开销)。两个 45s TTL 缓存在此路径上均被 force 绕过,形同虚设。


## 4. epubBookRepository 的 getBlock 读 orca.state 优先,写清单后立即读取可能拿到旧快照,与仓库既定 backend-first 规范相悖

- **审计维度**：缓存一致性
- **状态**：已修复（2026-07-26）

### 问题描述

epubBookRepository 内部 getBlock 先读 orca.state.blocks、miss 才查后端。但本仓库已两处明确记载 orca.state.blocks 在属性写入后可能是旧快照:irBlockCache.ts:17『orca.state.blocks 可能是旧快照(properties 不一定最新),会导致 IR 状态读回旧值』;同属书籍域的 bookIRPlanRepository.ts:32-34 特意改成 backend-first『Prefer get-block so post-write reads are not stuck on a stale orca.state.blocks snapshot』。而 epub 清单恰恰是典型的写后读检查点:runEpubImport 每章 persistManifest(epubImportService.ts:143/147),失败后用户重试时 resumeEpubImport(epubImportService.ts:162)和重复导入检查(epubImportService.ts:43)都经 loadManifestFromBook → getBlock 读取。若 state 快照落后于最近一次 persistManifest,resume 会按旧清单把已导入章节当 pending 重跑(entry.blockId 为旧值 null 时还会重新生成章节 HTML),findChapterBlockByIdentity 只能部分兜底,且清单状态可能被旧数据回退。

### 代码证据

epubBookRepository.ts:32-36:

  const cached = orca.state.blocks?.[blockId] as Block | undefined
  if (cached) return cached

### 修复建议

把 epubBookRepository.getBlock 改成与 bookIRPlanRepository.getBlock 相同的 backend-first(优先 invokeBackend("get-block"),失败记录日志后回退 orca.state),使 loadManifestFromBook / ensureChaptersHeading / ensureInlineReference 的写后读取可信。

### 独立验证结论

属实。(1) epubBookRepository.ts:32-36 的 getBlock 确为 state-first,与 evidence 逐字一致;persistManifest/setBookEpubProperties(:38-75)写后无快照刷新。(2) staleness 前提被仓库自身证据三重确认:irBlockCache.ts:17 明确记载 orca.state.blocks 属性写入后可能是旧快照;bookIRPlanRepository.ts:31-47 同名函数为此专门改 backend-first 并注明理由;模块文档/问题经验.md:304 记录同一书籍域由此快照滞后引发的已验证回归。(3) 写后读路径真实:epubImportService.ts:143/147/207/248/252 persistManifest 后,resumeEpubImport(:162)、重复导入检查(:43)、epubManifestChapters.ts:22 均经 loadManifestFromBook→getBlock 读回;EpubImportWizard.tsx:160-167 的 resume 是同会话一键触发,且 importEpub 已导航到书页(:96)使书块驻留 state,state-first 必命中可能过期的条目。(4) 缓解不完整:findChapterBlockByIdentity(epubBookRepository.ts:181)只能兜底已写入 chapterKey 属性的章节;PartialChapterImportError 场景(建页后属性写失败,blockId 仅存清单)读到旧清单会丢 blockId 并 createChapterPage 重复建页(:328-332),旧清单还会被回写造成状态回退。severity=medium 恰当:有真实重复建页/清单回退路径但需 staleness 窗口且多数场景被 identity 查询兜底,未夸大。

## 5. 查询块后端查询失败被静默转为空数组，用户被告知“查询结果为空”

- **位置**：`src/srs/blockCardCollector.ts:88`
- **审计维度**：错误可见性
- **状态**：已修复（2026-07-26）

### 问题描述

getQueryResults 在 orca.invokeBackend("query") 抛错时 console.error 后 return []，调用方无法区分“查询真的为空”与“查询失败”。main.ts 从查询块发起复习会话时，拿到 [] 就向用户弹 info 通知“查询结果为空”并直接返回——一次瞬时后端失败被伪装成正常空结果，用户不会意识到需要重试，违反 AGENTS.md“不得用 return [] 掩盖失败读取”的硬规则。contextMenuRegistry.tsx:301/350 也走同一路径。

### 代码证据

src/srs/blockCardCollector.ts:88-91:
  } catch (error) {
    console.error(`[blockCardCollector] 执行查询失败:`, error)
    return []
  }
配合 src/main.ts:540-544:
  const queryResults = await getQueryResults(blockId)
  if (queryResults.length === 0) {
    orca.notify("info", "查询结果为空", { title: "SRS 复习" })
    return
  }

### 修复建议

让 getQueryResults 在查询执行失败时直接 rethrow（或返回带错误标记的结构如 { ok: false, error }），由 main.ts / contextMenuRegistry 的调用点捕获后用 orca.notify("error", …) 明确告知“查询执行失败，请重试”，与“结果为空”的 info 文案区分开。

### 独立验证结论

证据属实：blockCardCollector.ts:88-91 的 catch 在 console.error 后 return []，与第 81-84 行正常空结果的返回值无法区分。main.ts:540-544 拿到 [] 后弹 info 通知"查询结果为空"直接返回；contextMenuRegistry.tsx:301-309/350-354 同样把 [] 当作正常空结果，其外层 try/catch（317/379）因异常已在 getQueryResults 内被吞而永远不会因查询失败触发。内部调用方 blockCardCollector.ts:137/232 同样被波及。该路径是右键菜单复习的主流程，非死代码，无重试或别处上报等缓解。AGENTS.md:17 明文禁止用 return null/[] 掩盖失败读写，此处直接违反。影响为瞬时后端失败被伪装成正常空结果、误导用户，无数据丢失，severity=medium 恰当。
