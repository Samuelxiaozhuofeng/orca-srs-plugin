## 1. IR 阅读断点的 keyup 捕获 debounce 在切卡竞态下会把新卡的块写入旧卡断点

- **位置**：`src/hooks/useIRReadingBreakpoint.ts:294`
- **审计维度**：React UI
- **状态**：已修复（2026-07-26）

### 问题描述

IRSessionShell 在会话根节点挂了 onMouseUp/onKeyUp={breakpoint.scheduleCapture}(IRSessionShell.tsx:656-657)。IR 快捷键在 keydown 触发 handleNext(useIRShortcuts.ts:116),handleNext 先 await breakpoint.flush()(flush 开头会清 debounce),但随后到来的 keyup 会再次调用 scheduleCapture,设置一个 180ms 的定时器,闭包捕获的是旧 cardId。performNext 完成后 removeCurrent 切换到新卡并重渲染 DOM;定时器到期时 captureFromVisibleBlock 仍用旧 cardId 闭包,但 containerRef.current 已指向新卡内容,于是把新卡的可见块 ID 作为 resumeBlockId 持久化到旧卡(persist 只检查闭包里的旧 cardId 非空)。本地后端延迟通常小于 180ms,焦点在正文内用键盘翻页时这是常见路径,会覆盖 flush 刚写入的正确断点,导致旧卡下次恢复到错误位置或恢复失败。值得注意的是 scroll 路径已经有 shouldAllowScrollVisibleCapture({ listeningForCardId, activeCardId }) 守卫(第 405-411 行),而交互捕获路径没有对应守卫;卡片切换时也没有任何 effect 清理 debounceRef(第 443-448 行仅在 unmount 清理)。

### 代码证据

src/hooks/useIRReadingBreakpoint.ts:294-301 `const scheduleCapture = useCallback(() => { ... debounceRef.current = window.setTimeout(() => { debounceRef.current = null; captureNow() }, DEBOUNCE_MS) }, [captureNow])`;443-448 仅 unmount 清理:`useEffect(() => () => { if (debounceRef.current != null) window.clearTimeout(debounceRef.current) ... }, [clearScrollDebounce])`;对比 405-411 scroll 路径有 `shouldAllowScrollVisibleCapture({ suppressActive..., listeningForCardId, activeCardId: activeCardIdRef.current })` 守卫;触发点 src/components/incremental-reading/IRSessionShell.tsx:656-657 `onMouseUp={breakpoint.scheduleCapture} onKeyUp={breakpoint.scheduleCapture}`

### 修复建议

两处修补:1) 在 cardId 变化的 effect(或现有 443 行 cleanup 改为依赖 cardId)里清除 debounceRef;2) 在 captureNow/captureFromSelection/captureFromVisibleBlock 入口加与 scroll 路径相同的守卫——比较闭包 cardId 与 activeCardIdRef.current,不一致则丢弃本次捕获。已有的 activeCardIdRef 就是为此准备的,复用即可。

### 独立验证结论

属实。核实链条:(1) IRSessionShell.tsx:656-657 会话根节点绑定 onKeyUp={breakpoint.scheduleCapture},且 hook 在 shell 级别单实例挂载(IRSessionShell.tsx:218),切卡走 removeCurrent(426-438)只换 queue 内容不重挂 hook,debounceRef 跨卡存活;(2) useIRShortcuts.ts:98-116 Enter 在 keydown(document 捕获阶段)触发 handleNext,keydown 的 preventDefault 不抑制后续 keyup,keyup 会冒泡到根节点;(3) useIRSessionCardActions.ts:107-115 handleNext = await flush() → performNext → removeCurrent,而 flush(useIRReadingBreakpoint.ts:303-324)含最少 50ms 等待+后端往返,keyup 恰落在此窗口内,scheduleCapture(294-301)重新armed 180ms 定时器,闭包 captureNow 携带旧 cardId;(4) captureFromVisibleBlock(259-286)与 persist(183-210)只检查闭包 cardId,无 activeCardIdRef 比对——对比 scroll 路径确有 shouldAllowScrollVisibleCapture 守卫(405-411;irBreakpointRestore.ts:162-170),且 443-448 仅 unmount 清理 debounceRef,startRestore 只清 scrollDebounce(330-332);(5) BreakpointSaveChannel 按 cardId 分配版本(191/195),过期捕获分配到比 flush 写入更新的版本号,合法覆盖正确断点。鼠标路径因 mouseup 先于 click(flush 会清掉刚 armed 的定时器)而安全,键盘路径顺序相反,正是发现所述的不对称。定时器到期(约 keydown+280ms)时本地后端下切卡渲染通常已完成,containerRef.current 已是新卡 DOM,新卡块 ID 被持久化为旧卡 resumeBlockId,静默覆盖 flush 刚写的正确断点,旧卡下次恢复失败或错位。发生在键盘翻页这一主路径上、静默损坏断点数据且无任何缓解,维持 high。

## 2. createCloze 每次新增填空都会把同块所有已存在 cloze 的 SRS 状态重置为新卡

- **位置**：`src/srs/clozeUtils.ts:319`
- **审计维度**：领域正确性
- **状态**：已修复（2026-07-26）

### 问题描述

createCloze 成功插入新填空后，遍历块内全部 cloze 编号并对每一个调用 writeInitialClozeSrsState。该函数（src/srs/storage.ts:467-481）无条件写入 createInitialSrsState 生成的初始状态（reps=0、stability/interval 归零、due=今天+offset），不检查该编号是否已有复习历史。因此用户在一张已复习过的 cloze 卡上追加新填空（编辑器 alt+z / `${pluginName}.createCloze` 命令 → irClozeCommandService.createClozeFromEditorCommand → createRegularCloze 路径），会把 c1、c2 等所有旧填空的 FSRS 进度全部清零，复习历史不可恢复。这是渐进使用中的常见操作（今天挖 c1，隔几天再挖 c2），属于静默数据丢失。仓库其它路径已有正确范式：reviewCardFactory.ts:128 与 irConversionService.ts:226 都用 ensureClozeSrsState（仅在无 srs.cN.* 前缀属性时才初始化）。现有回归测试 clozeUtils.test.ts 只覆盖首个填空，未覆盖二次挖空场景。

### 代码证据

src/srs/clozeUtils.ts:305,316-319:
    const clozeNumbers = getAllClozeNumbers(finalBlock.content, pluginName)
    ...
    for (let i = 0; i < clozeNumbers.length; i++) {
      const clozeNumber = clozeNumbers[i]
      const daysOffset = clozeNumber - 1
      await writeInitialClozeSrsState(blockId, clozeNumber, daysOffset)
    }

src/srs/storage.ts:467-479（writeInitialClozeSrsState 无条件覆盖）:
  const initial = createInitialSrsState(dueDate)
  await saveClozeSrsState(blockId, clozeNumber, initial)
对比 src/srs/storage.ts:671-682 ensureClozeSrsState：`if (!hasPropertyWithPrefix(block, prefix))` 才写初始状态。

### 修复建议

循环内改用 ensureClozeSrsState(blockId, clozeNumber, daysOffset)，仅对本次新建的 nextClozeNumber 保留 writeInitialClozeSrsState（避免复用已删除编号时继承孤儿 srs.cN.* 旧状态）。补一条回归测试：块已有 c1（reps>0）时二次挖空 c2，断言 c1 的 srs.c1.* 未被覆盖，并按仓库规则记入 模块文档/问题经验.md。

### 独立验证结论

属实。src/srs/clozeUtils.ts:305,316-319 中 createCloze 成功后对 getAllClozeNumbers（clozeUtils.ts:50-71，返回块内全部编号）返回的每个编号调用 writeInitialClozeSrsState；该函数（src/srs/storage.ts:467-481）无条件用 createInitialSrsState（algorithm.ts:331-334，createEmptyCard 新卡）经 saveSrsStateInternal（storage.ts:356-389）setProperties 覆盖 srs.cN.* 全部属性，无存在性检查——对比 ensureClozeSrsState（storage.ts:671-682）有 hasPropertyWithPrefix 守卫。调用路径为活代码主路径：registry/commands.ts:95-136 注册 alt+z 的 createCloze 命令 → irClozeCommandService.ts:30-58 createClozeFromEditorCommand，普通 SRS cloze 卡（无 ir.due，见 irHybridExtract.ts:10-14）二次挖空必走 createRegularCloze=createCloze。无下游缓解：命令 undo 仅打日志（commands.ts:126-131），reviewCardFactory 的 ensureClozeSrsState 在属性已被覆写（reps=0）时不会恢复，操作还弹成功通知，属静默不可恢复的复习历史丢失。二次挖空是常规操作，severity=high 不夸大。
